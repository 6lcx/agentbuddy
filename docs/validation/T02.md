环境：Windows、Python 3.12.3、Node 24.17.0、Edge 无头浏览器。
依赖：SQLAlchemy 2.1.8、Alembic 1.20.1、filelock 4.2.10，完整版本以 backend/uv.lock 为准。

## 实现与局部设计

- 初始 Alembic revision 0001_queue 创建 operations、worker_instances、events。业务配置、项目、Run/Task 表随对应任务增量迁移，不将目标模型全部建为空壳表。
- data 默认位于仓库根目录，独立于启动工作目录；DATA_DIR 可统一设置为绝对路径。SQLite 使用 WAL、foreign_keys 和 5 秒 busy_timeout；创建 tmp/skills/projects/uploads 目录。
- SQLAlchemy Core 仓储使用短 BEGIN IMMEDIATE 事务。领取与 running 事件、结果与终态事件分别同事务提交。异步处理期间不持有写事务。
- Worker 每次启动有独立 UUID/boot_id；领取生成 claim_token，完成必须匹配运行状态、Worker 和 token，防止迟到/重复结果。
- Worker 持有 OS 文件锁，迁移复用同一锁，防止两份调度器或运行时迁移。每 5 秒心跳，30 秒无心跳显示 stale；不凭过期心跳抢占仍持锁的 Worker。
- 重启持锁后，旧 Worker 标 lost、在途 Operation 标 failed（worker_interrupted）；queued 保留，不自动重放。停止时不再领取，默认最多等待 10 秒，超时取消在途处理并标失败。
- Operation 当前单槽执行；业务 Run 并发和等待恢复属于后续任务。
- 新增统一前缀下的系统状态、后台存储诊断、Operation 结果/事件接口，均有 OpenAPI 响应模型。未迁移返回 503，存活健康接口仍可用。
- 服务状态页展示数据库、Worker、最后心跳和后台检查结果；存储诊断由真实独立进程执行临时文件读写及 SQLite 设置检查。

后端关键覆盖：

- 初次/重复迁移、schema 与 metadata 一致；关闭 GC 后依然可以重命名数据库文件，验证显式释放句柄。
- spawn 两个独立进程通过 Barrier 同时竞争一条任务，仅一个领取成功且仅一条 running 事件。
- 事件写入故障时整体回滚，外键拒绝孤立事件；错误 token、迟到/重复结果不能改写终态。
- 真实 Worker 子进程执行存储诊断，重复启动被拒绝，活跃 Worker 期间迁移被拒绝。
- 强制结束在途 Worker 子进程后，新 Worker 标记旧操作失败、保留并执行 queued，不重放中断任务。
- 处理期间心跳继续，其他请求可以入队；正常停止允许当前处理完成，超时停止能取消；操作超时和未知类型明确失败。
- API 提交→Worker 执行→读取持久结果/有序分页事件；重新创建 API 后结果仍在；未迁移返回 503。

浏览器覆盖：默认 /app + /api/v1、自定义 /workspace + /custom/api/v1 下，连接、嵌套路由刷新、故障重试、SQLite/Worker 状态展示及真实后台存储诊断均通过。

## 发现与修复

1. 创建接口提交后重读记录可能遇到 Worker 已将 queued 改为 running，造成创建响应校验失败。改为在创建事务内返回创建快照，之后通过查询接口获取实时状态。真实 Worker 浏览器回归通过。
2. sqlite3 连接上下文不会自动关闭连接，曾导致 Windows 临时目录清理失败。迁移改用 contextlib.closing，补充禁用 GC 的句柄释放回归；最终完整脚本清理成功。
