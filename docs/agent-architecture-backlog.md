## 2. 上下文管理需求

### CTX-01：阈值压缩与完整请求预算

实施前状态：主任务开始前，当历史正文估算量超过 `context_size - max_output_tokens - 4096` 时尝试压缩。不是百分比阈值，也没有在每次 Agent 模型调用前统一执行压缩。

希望实现：

- 将 system prompt、工具定义、摘要、近期消息、工具结果和输出预留统一纳入预算。
- 设置可配置的提前触发阈值和压缩后的目标占用，避免直到接近硬上限才处理。
- 主 Agent 和子 Agent 都适用；执行过程中持续检查上下文增长。
- 不拆开必要的工具调用/结果配对，不静默删除当前请求。
- 压缩失败、当前请求过大、预算耗尽时提供明确状态和处理建议。

待确认：触发比例、目标比例、估算方式及不同模型的预留策略。

验收方向：长历史和大工具结果能够触发处理；完整请求仍在窗口内；当前需求和工具交互结构不被破坏。

### CTX-02：持久摘要与增量更新

实施前状态：按完整历史轮次生成本轮摘要，保留近期交互和当前请求；摘要模型调用计入预算。摘要没有跨运行持久化复用，下轮可能重复摘要。

希望实现：

- 摘要保存到持久存储，带版本、覆盖消息范围和来源引用。
- 只摘要新增加的历史，避免每轮从头处理。
- 明确保留用户约束、已确认事实、决策、待办、文件路径及未解决问题。
- 区分事实、假设和待确认信息，不把历史资料中的指令提升为系统规则。
- 保留原始历史用于回查；摘要错误可修订或重新生成。
- 摘要调用、失败及重试都受预算约束。

待确认：摘要结构、更新时机、最大长度、失效与重建规则。

验收方向：多轮修改后关键约束仍可追溯；重启后可复用摘要；不会重复支付全部历史的摘要成本。

### CTX-03：统一的大结果存盘与引用读取

实施前状态：脚本日志可存盘，并返回截断预览和日志引用；保存的日志本身也有上限。MCP 等返回值尚未统一转成存盘引用。

希望实现：

- 工具返回超过阈值时，把结果保存为运行产物，在上下文中只返回必要摘要和引用。
- 统一覆盖脚本日志、MCP 返回、文件读取和子任务结果。
- 引用包含标识、路径或读取接口、类型、大小、完整性信息，以及截断标记。
- 支持按需分页、范围读取或搜索，不要求模型重新加载整个结果。
- 设置磁盘额度、保留期限和清理规则；需要恢复的引用在 checkpoint 有效期内不能被删除。
- 区分“完整结果已存盘”和“仅保存部分结果”，不得把截断日志称为完整内容。

待确认：落盘阈值、预览长度、单结果上限、保留期限和读取工具接口。

验收方向：超大结果不撑爆上下文；模型可以凭引用取回所需片段；缺失或损坏引用明确失败。

### CTX-04：真正的执行 checkpoint 与断点恢复

实施前状态：成功文件版本可以作为新运行的文件起点。它不包含完整 Agent 执行状态，不是工具级或模型调用级 checkpoint。

希望实现：

- 定义可安全保存的执行边界，并持久化恢复所需的状态版本。
- 保存消息边界、摘要版本、任务计划、子任务状态、预算消耗、文件基线、结果引用和待处理确认。
- 明确记录工具操作的未开始、执行中、成功、失败及结果未知状态。
- 恢复时校验模型/工具/Skill 配置及文件引用兼容性。
- 外部写操作不能盲目重放；通过幂等键、结果查询或人工核对解决结果未知情况。
- 不默认承诺任意机器指令处恢复，先选择明确的安全边界。

待确认：checkpoint 频率、保存粒度、保留数量、恢复入口，以及是否先只支持工具完成后的边界。

验收方向：强制终止 Worker 后可从受支持边界恢复；预算不重置；已完成外部操作不重复执行；成功版本不被覆盖。

### CTX-05：稳定前缀与缓存友好压缩

用户提出的核心要求：**压缩时保留 checkpoint 之前的内容不变，争取复用 KV cache；优先处理边界之后新增的内容。**

希望实现：

- 明确定义缓存前缀边界，与执行 checkpoint 建立关联，但不把二者混为一谈。
- 在一个上下文周期内保持稳定前缀和序列化顺序，避免无必要地重写前部消息。
- 对新增内容进行增量处理；旧摘要保持稳定，直到确有必要创建新的摘要基线。
- 前缀过大或达到窗口限制时允许建立新基线，记录这次轮换及其缓存影响。
- 按模型供应商的实际能力实现适配，不承诺所有供应商使用同一种缓存机制。

技术边界：

- 执行 checkpoint 保存应用状态，不等于保存远程模型的 KV cache。
- 缓存命中主要减少重复计算、延迟及相应输入费用，不会让保留的内容不占上下文窗口。
- 压缩减少上下文长度；修改已有前缀可能影响缓存复用，二者存在取舍。
- 不能无限保留 checkpoint 之前的全部内容，必须定义基线轮换机制。

待确认：固定前缀组成、边界位置、后缀压缩方法、基线轮换条件及各供应商适配范围。

验收方向：验证请求前缀是否稳定，采集供应商缓存命中指标，对比压缩前后总成本与延迟，而非仅凭代码推断收益。

参考：[DeepSeek 上下文缓存官方说明](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)。实际行为以实施时的接口与实测为准。

### CTX-06：可观测性

建议记录：

- 每次请求的上下文估算、实际 usage、输出预留及触发原因。
- 压缩前后大小、覆盖范围、摘要版本、模型调用成本和失败原因。
- 大结果落盘数量、引用读取次数及磁盘使用量。
- checkpoint 保存/恢复次数、恢复失败原因及未知副作用数量。
- 供应商提供的缓存命中/未命中 token 数；不支持时明确标记未知。

不得把不同模型、不同工作负载或不同缓存状态的测试数据混为一个优化结论。

### CTX-07：渐进式披露上下文

提出日期：2026-11-11。初始状态：仅补文档。现已按后续用户授权实施T22。

目标：先提供足以发现信息的目录与描述，再按任务需要加载说明、具体资料和结果片段。它是 Agent 的上下文组织方式，由软件工程提供信息分层、读取接口和运行约束，Agent 在这些约束内判断需要哪些信息。

#### 实施前已有的部分

- Skill 元数据进入初始提示：ID、名称和用途描述，而非一开始注入所有 Skill 正文。
- `load_skill` 按需加载所选 Skill 的详细信息，并检查该 Skill 是否属于本轮能力范围及包完整性。
- `read_skill_file` 支持加载 Skill 后按路径和偏移读取参考文件。
- 部分办公及脚本工具要求先加载对应 Skill，形成程序约束，而不只是提示词要求。
- 脚本日志有存盘与预览引用的基础，但保存内容有上限，不能视为统一的大结果管理。

现状代码入口：`backend/src/agentbuddy/runtime/executor.py` 的初始能力描述，以及 `backend/src/agentbuddy/runtime/tools.py` 的 Skill 加载、参考文件读取和日志返回。上述能力不代表整个上下文系统已完成渐进式披露。

#### 实施前缺口（T22状态见顶部）

- MCP 工具信息随连接器配置进入提示，没有统一的“先发现工具、再加载详细定义”机制。
- 项目文件缺少统一的目录摘要、局部搜索和按需读取策略；有文件读取工具不等于已经实现分层披露。
- MCP、脚本、文件读取和子任务结果没有统一的摘要与引用返回协议，可能把大量原文直接带入上下文。
- 没有统一记录哪些内容已经加载、加载到哪个版本、是否重复读取，以及何时可以替换为摘要或引用。
- 子 Agent 的资料范围还未严格按显式最小输入清单组织；工作目录复制也不等于上下文最小化。
- 没有统一评估加载成本、遗漏关键信息、工具发现失败和最终任务正确率。

#### 后续实现方案

以下保留协商时的设计方向，已落地接口及边界以顶部状态及T22规格为准。

1. **建立分层目录。** 初始层只提供必要的能力名称、用途、适用条件和资源引用；第二层提供任务相关的操作说明或工具参数定义；第三层按需提供参考章节、数据片段、模板及结果内容。必须始终生效的关键约束仍保留在基础上下文中，不能全部藏到可选资料里。
2. **提供统一发现与读取入口。** 在现有 Skill 工具上扩展能力搜索、资源列表、文件/结果范围读取等接口。先复用本机文件及 SQLite，不预设必须引入向量库或外部检索服务。
3. **真正延迟注入。** 工具目录与完整 schema 分开；加载选定工具后，只把需要的定义加入后续模型请求。不同供应商若不支持同样的动态工具方式，由适配层明确处理，不能后台仍注入全部定义却称为按需加载。
4. **统一结果引用。** 与 CTX-03 共用存盘协议：返回简要说明、结果 ID、类型、大小、版本或 hash、截断状态及读取入口；大结果通过分页、范围读取或搜索获取。
5. **维护加载状态。** 按运行或 Agent 记录资源 ID、版本、已读范围和来源；对重复加载返回已有引用或必要增量。资源变更时明确失效或重新加载，不静默混用版本。
6. **接入预算与生命周期。** 与 CTX-01/CTX-02 配合，在读取前评估剩余空间；已经加载的内容不会自动消失，需要明确的摘要、引用替换或保留策略。保留必要的工具调用/结果结构，并尊重 CTX-05 的稳定前缀边界。
7. **覆盖子 Agent。** 与 AGENT-04 共用最小输入清单；派发目标、约束和必要引用，子 Agent 自行按需读取，汇总时返回有界结果及证据引用。
8. **接入恢复与观测。** checkpoint 保存资源引用、版本和加载状态；恢复时检查引用是否有效。记录发现、加载、重复读取、失败、上下文占用及调用成本。

#### 示例流程

任务：“根据销售表生成季度汇报 PPT。”

- 初始只提供用户需求、附件目录和 Excel/PPT 技能描述。
- Agent 加载 Excel 说明，读取工作表名称、列名和少量样例。
- 通过脚本或范围读取取得相关数据，汇总结果存盘并返回引用。
- Agent 加载 PPT 说明，读取选定模板；需要图表时再读取相关说明。
- 生成文件后返回产物、关键结论和验证证据引用，不向总控回传全部原始数据。

#### 与其他机制的关系及边界

| 机制 | 主要职责 |
| --- | --- |
| 渐进式披露 | 决定何时加载哪些信息，以及加载到什么粒度 |
| 大结果存盘 | 保存原始结果，提供可追溯的按需读取引用 |
| 摘要压缩 | 缩减已经积累的上下文 |
| checkpoint | 保存可恢复的执行状态和引用关系 |
| 缓存友好前缀 | 尽量复用稳定内容的计算；不能由延迟加载本身保证命中 |

不能只在提示词中写“按需读取”就判定实现完成，也不能把权限隔离、文件工作目录隔离与上下文披露范围等同。动态发现和多次读取可能增加延迟；应测量任务质量与总成本，不能只比较首次请求的 token 数。

#### 待确认问题

- 初始目录包含哪些字段，目录本身过大时如何搜索和分页？
- 哪些内容必须常驻，哪些说明允许延迟加载？
- 自动加载与 Agent 主动请求的边界在哪里？
- 每次读取大小、预览长度、重复加载规则及总读取预算如何设置？
- 是否按运行冻结资料版本，资料更新如何反映到下一轮？

#### 验收标准

- 未用到的 Skill 正文、参考资料和 MCP 完整工具定义不进入模型请求，使用实际请求内容验证。
- Agent 能从目录发现正确能力，按需加载并完成真实任务；必需资料缺失时明确提示。
- 大文件、大工具结果不会整份注入；能够通过引用定位所需内容，且截断、版本变化、损坏或引用失效可观察。
- 重复加载不反复扩张上下文；确需刷新时获取正确版本。
- 子 Agent 只获得声明的必要输入和引用，不能因为工具发现扩大既有能力范围。
- 与压缩、稳定前缀和 checkpoint 联动后，仍能恢复资源访问并追溯依据。
- 用相同任务比较全量注入与渐进式披露：记录完成质量、上下文大小、模型/工具调用数、总成本和延迟，不只展示 token 降幅。

参考：[Anthropic Agent Skills](https://www.anthropic.com/research/equipping-agents-for-the-real-world-with-agent-skills)、[上下文工程说明](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)。实现时以实际框架和供应商接口为准。

## 3. 多 Agent 架构需求

### AGENT-01：保留已有协作能力

当前已有：固定总控、已有专家候选范围、单层派发、子任务并发上限 3、依赖排序、循环依赖检查、独立 Agent 实例、独立工作目录、文件冲突处理及共享运行预算。

当前不足：这些机制主要校验和执行计划，没有完整判断任务是否值得派发；子任务尚无独立可配置轮数和调用配额。

后续改进需保留现有协作行为，不引入无限递归派发。

### AGENT-02：三条任务派发准则

用户提出希望加入的准则：

1. **可并发**：任务具有能够独立推进的部分。
2. **上下文可隔离**：能够提供明确、有限的输入，不依赖隐含共享状态或主 Agent 的全部历史。
3. **执行轮次大于 3**：任务足够复杂，派发收益值得覆盖创建、传递和汇总成本。

待确认的规则语义：

- “大于 3”是否指派发前**预计**超过 3 轮；不是先强制执行 3 轮后才能派发。
- “一轮”如何定义：一次模型决策，还是一次模型与工具交互周期；不能与用户聊天轮次混淆。
- 三条是否必须同时满足，是否允许用户显式指定专家作为例外。
- 有依赖但需要专长的串行子任务如何处理；不应在没有确认的情况下直接删除现有依赖调度能力。
- 门槛是否可配置，以及不同角色是否使用不同值。

实现方向：派发计划声明理由、预计轮次、输入/输出、依赖、可隔离性和副作用；运行层检查可确定的硬约束。预计工作量与语义独立性不能仅凭模型自报视为可靠事实，应记录依据并用实际执行结果评估。

验收方向：简单任务不被无意义拆分；符合规则的独立任务可并发；资料不足或依赖冲突时阻止或调整派发；决策可审计。

### AGENT-03：每个 Agent 的轮数与预算

实施前状态：主/子 Agent 均使用硬编码 `max_iters=50`；主要共享整轮调用与时长预算，没有按专家/子任务独立配置的完整机制。

希望实现：

- 明确轮数定义，分别设置主 Agent、总控和子 Agent 的最大轮数。
- 支持专家默认值和子任务限制；解析后冻结进运行快照。
- 子 Agent 同时受自身轮数/调用/时长限制，以及整个任务的共享总预算限制。
- 明确重试、摘要调用、委派和工具调用分别消耗哪种额度，避免将所有指标混成一个轮数。
- 达到上限后返回明确终态、已完成结果和未完成事项，不能无限自我修复。
- 防止通过重新派发或重启子 Agent 绕过总预算。

待确认：默认值、允许范围、覆盖优先级、预算分配方式、失败重派策略。

验收方向：单个子 Agent 超限不会无限占用资源；并发下额度不超用；重新派发不重置总消耗。

### AGENT-04：上下文隔离与有界回传

实施前状态：子 Agent 使用独立实例，接收任务指令与依赖结果，不直接共享主 Agent 的完整消息历史；但工作目录会复制项目文件，尚不是最小资料集。

希望实现：

- 每个子任务具有显式输入清单：目标、约束、必要文件引用、依赖结果和验收要求。
- 按需提供资料，避免向每个 Agent 复制完整对话及全部文件内容。
- 子任务返回结构化结果、证据、产物引用、失败原因及未完成项。
- 大结果通过引用回传，避免多个子 Agent 的输出一起撑爆总控上下文。
- 文件冲突、未知外部结果和失败依赖必须显式处理。
- 子 Agent 同样使用统一上下文管理与 checkpoint 机制。

验收方向：子任务不依赖未声明信息；能力和上下文不意外扩散；汇总端能追溯结果且不加载全部原始日志。

## 4. 建议实施顺序（尚未作为执行指令）

1. 确定轮数、派发门槛、阈值和 checkpoint 的具体语义。

3. 实现持久摘要、增量压缩及主/子 Agent 共用入口。
4. 实现受支持边界的 checkpoint 与副作用恢复协议。
5. 实现稳定前缀和缓存指标，按实测调整压缩策略。
6. 实现派发准则、每 Agent 配额，并完成多 Agent 故障与并发验证。
