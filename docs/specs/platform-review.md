# 平台 Spec 整体评审

日期：2026-11-10
评审对象：platform-v0.1.md（内容版本 0.5）及用户最新需求。
性质：历史评审记录。用户已采纳推荐的首版组合并要求重构 Spec，当前需求以 [平台规格 v1.0](platform.md) 为准；本文中的“待接受”“未获确认”等措辞保留评审时点语境，不代表当前状态。

## 最新约束

Skills、MCP、创建 Agent 并绑定能力、Web、多 Agent、前后端分离、Python 后端与 React 前端、统一路由前缀、统一后端 API 前缀、SQLite；不要求沙箱或安全体系。

Python + React 理解为后端 Python、前端 React（推荐 TypeScript）。此前强隔离相关承诺与最新约束冲突，不应继续作为已确定验收要求。

## 评审结论

推荐可信用户使用的单机部署 Web 工作台，优先完整实现能力装配、有限多 Agent 协作和文件交付。最新技术要求可行；主要问题是既有产品范围过大，以及无沙箱和任意用户代码执行下仍承诺强用户隔离的矛盾。

| 问题 | 影响 | 最推荐调整 |
| --- | --- | --- |
| 公网开放多用户 + 任意上传脚本/MCP + 无沙箱 | 用户代码以宿主进程权限运行；按用户过滤数据库无法保证执行隔离 | 首版定位可信用户的本地/内网工具；可保留基本用户归属，但明确不提供强隔离 |
| 三种执行位置同时建设 | Windows 桥接引入安装、连接、生命周期、文件回传和离线恢复 | 首版远程 MCP + 后端所在机器的进程型 MCP；跨设备 Windows 组件后置，需用户接受该变更 |
| 动态组团 + 自动重分派 + 多层协作 | 故障原因和文件责任难定位，增加模型成本 | 保留动态选人，但使用固定总控角色，只从已有专家中选成员；单层协作、有限并发 |
| 仅写绑定 Skill，没有运行机制 | 容易只做出配置 CRUD，无法真实执行 | 按需加载 Skill 指令，提供读写文件、运行脚本工具及模型-工具执行循环 |
| SQLite 与高频并发写 | 多 Agent 同时写日志易竞争写锁 | 单机 SQLite、短事务、批量事件写入；模型调用不持有事务；文件放文件系统 |
| 无沙箱被理解为无需执行管理 | 脚本卡死、文件覆盖、任务取消失效 | 使用普通子进程，保留工作目录、超时、取消与输出限制；它们不是安全隔离 |
| 通用文件项目意味着无限格式兼容 | 无法判定完成，可能交付不可打开的文件 | 通用目录模型，逐类声明已验证格式；按文件类型检查实际可用性 |
| 自动恢复过宽 | 反复尝试无法修复缺失依赖，外部写入可能重复 | 瞬时故障有限重试；明确依赖错误直接报告；结果未知的外部写入不盲目重复 |
| 历史版本做成完整版本管理系统 | 不必要地增加分支合并复杂度 | 成功交付时保存完整目录快照；后续在最新成功版本上修改；保留历史下载 |
| 路由统一前缀含义不明确 | 前端页面与 API 混用，部署子路径失效 | APP_BASE_PATH 与 API_PREFIX 分开集中配置 |

## 推荐实现形态（供后续 Plan 参考）

- React + TypeScript + Vite：配置页面、任务会话、运行状态、文件与版本查看。
- Python + FastAPI：业务 API、能力注册和模型适配。
- 独立 Python 任务执行进程：负责执行循环、有限并行、子进程和预算；API 快速返回任务标识，避免将任务绑定到 HTTP 请求生命周期。
- SQLite：配置、关系、任务状态、事件和版本元数据。普通磁盘目录：Skill 包、工作文件及版本快照。首版不要求 Redis、PostgreSQL、对象存储或容器沙箱。
- MCP SDK：远程服务与后端机器的进程型服务；MCP 本身不实现多 Agent 编排。
- 运行内核先定义明确接口与状态；是否引入编排框架留到 Plan，不把框架名字当作产品功能。
- 任务进程重启后将未完成运行标为中断，保留结果并允许重新运行；首版不承诺任意中断点精确恢复。

前缀建议（推荐值，不是已确认路径）：页面 /app，API /api/v1。页面示例 /app/agents；接口示例 /api/v1/agents、/api/v1/runs、/api/v1/runs/{id}/events、/api/v1/projects/{id}/versions。流式事件、文件下载也使用 API 前缀。React Router 基路径、静态资源基路径和部署回退规则需一致；前后端分离不要求部署在不同域名。

## 推荐首版闭环

1. 注册模型、导入 Skills、连接 MCP。
2. 创建多个 Agent，配置角色、模型、Skills、MCP 工具与协作者。
3. 用户选择专家或自动协作入口，提交任务与文件要求。
4. 固定总控在候选范围内选择专家并拆分子任务；独立任务有限并行，有依赖的任务等待。
5. 各子任务写各自工作目录，总控负责最终目录汇总与文件检查，避免同时修改同一文件。
6. 展示过程、支持停止和失败原因；真实生成并下载项目文件。
7. 保存成功交付快照，后续通过对话产生下一版本。

保留时长和调用次数预算。预算口径按原 Spec 评审，默认数值留作可配置参数；待用户回复时建议停止执行计时，另设会话过期时间，避免用户思考消耗执行预算。设备离线恢复等待仍计入执行时长。此项是对原草稿计量建议的修正，未获用户确认。

## 优先验收

- 同一 Skill 绑定两个 Agent、一个 Agent 绑定多个 Skills，运行中可观察实际加载。
- 一个 MCP 工具真实调用成功；一个 Skill 脚本真实生成文件。
- 两个专家确实并行执行，最终目录没有相互覆盖的产物。
- 任务失败、超时或取消后仍能查看原因与已有文件。
- 修改产生 V2，V1 内容不变且仍可下载。
- 配置 API 前缀后，业务接口、事件流与下载链接均生效。
- 数据库写入竞争不阻塞整个接口服务，运行模型期间不持有数据库写事务。

## 原 Spec 需要的处理

最新无沙箱约束已经覆盖旧隔离假设。尚未自动删除此前用户选择的 Windows 跨设备组件、开放平台及动态主专家选举：本评审建议收缩这些范围，需要用户采纳后统一重写。现阶段原 Spec 不应直接用于开发。
