## 1. 目标与依据

用户通过 Web 平台配置专家，为专家绑定多个 Skills 和 MCP 能力，选择专家或专家团提交任务，由主专家分派给多个专家同时处理，最终汇总交付完整的项目文件。

已确认：Web 产品形态；开放平台，不同用户各自配置和使用；首版支持主专家分派、多专家并行协作及通用项目文件交付。单专家仅调用用户预配置的协作专家；专家团由系统根据任务动态组建，候选范围为用户自己的专家和用户已启用的平台预置专家。Skills 来源为平台预置和用户上传包，支持执行附带脚本。模型由平台提供，用户从可用列表选择。当前只完成 Spec，不进入技术设计、开发计划或实现。

参考：../research/workbuddy-platform.md。调研中的技术栈及分期建议不是已确认需求。

MCP 首版范围已确认：远程服务、平台托管的进程型服务，以及用户电脑上通过本地连接组件接入的进程型服务。产品以 Web 为主入口，同时包含必要的本地连接组件；不等同于完整桌面工作台。

运行与迭代已确认：本地连接组件首版支持 Windows；发生子任务失败或设备离线时，自动尝试重分派或恢复，达到任务预算上限后停止；支持在同一项目中继续对话修改，并保留可下载的历史版本。

预算已确认：以总时长和模型/工具调用次数为限制维度；平台设置默认值和最高限额，用户可以在平台上限内调整。任一维度耗尽即停止；费用不作为本版已确认的任务停止条件。

## 2. 术语

- 专家：可复用的 Agent 配置，描述职责、行为要求及可用能力。
- Skill：可复用的任务方法说明，可以附带脚本、资料或模板；不等同于一个专家。
- MCP 连接器：平台访问外部工具或数据服务的连接配置。
- 运行位置：远程服务、平台隔离执行环境或用户设备；连接器必须明确对应其中一种位置。
- 本地连接组件：在用户设备上连接平台、启动或接入用户配置的 MCP 进程的组件。
- 能力绑定：定义专家可以使用的 Skills 和 MCP 工具范围，不代表每次运行必须全部调用。
- 任务运行：用户提交需求后的一次执行，有独立输入、状态、过程记录和结果。
- 多专家配置：平台中存在多个可选择的专家。
- 多专家协作：同一次任务由主专家分派给多个专家处理，并汇总结果；纳入第一版。
- 专家团：系统围绕当前任务，从允许的候选专家中动态选择主专家与成员形成的协作组合。
- 通用文件项目：按用户任务要求生成的目录及文件集合，不限定为软件或办公项目；不意味着所有格式均受到支持。
- 产物：任务生成的报告、文件或其他可交付结果。
- 项目版本：一次交付的完整文件集合，可独立下载；后续修改产生新版本，历史版本保持可获取。
- 恢复尝试：对失败步骤重试、恢复或重新分派，属于原任务的执行过程，不自动获得新的任务预算。

## 4. 候选需求与验收条件

下列需求是供评审的草稿。标为“建议”的行为尚未获得用户确认。

### R1 专家管理

用户可以创建和编辑专家，填写名称、职责说明及行为要求，并在发起任务时选择专家。

- AC1.1：保存两个不同专家后，用户可以在列表中区分并分别选择它们。
- AC1.2：缺少必填信息时，界面指出具体缺失项，不能出现看似保存成功但配置不可用的情况。
- AC1.3：用户可为专家指定协作专家；单专家入口的任务不能调用配置范围以外的专家，即使其他专家属于该用户。
- AC1.4：用户可以启用平台预置专家；未启用的预置专家不进入动态组团候选范围。
- AC1.5：用户从平台提供的可用模型中选择专家所用模型，第一版不要求用户提供模型 API 密钥。
- AC1.6（建议）：选定模型不可用时明确报错或提示重新选择，不静默换用其他模型。

### R2 Skills 管理与绑定

一个专家可绑定多个 Skills；同一 Skill 可复用于多个专家。

Skills 可来自平台预置或用户上传的 Skill 包，支持在任务中执行附带脚本。

- AC2.1：专家 A 可以绑定 Skill X 和 Y；专家 B 可以同时绑定 X。
- AC2.2：从 A 解绑 X 不会删除 X，也不会改变 B 的绑定。
- AC2.3：不可读取或格式不受支持的 Skill 显示明确错误，不能被标记为可用。
- AC2.4（建议）：运行详情能区分“允许使用的 Skills”和“实际加载的 Skills”。
- AC2.5：用户能够选择预置 Skill 或上传包含说明、资料及脚本的 Skill 包，再绑定给专家。
- AC2.6：验收任务实际执行一个 Skill 附带脚本，产生可验证结果；仅阅读脚本或声称执行不算通过。
- AC2.7（建议）：脚本运行受任务权限和资源限制约束，不能访问其他用户的文件或凭证；上传包本身不自动授予执行权限。
- AC2.8（建议）：脚本失败或缺少依赖时展示原因，不能将未生成的文件列为已交付。
- 待定义：包格式、支持的脚本语言及依赖范围、运行时间与资源上限。

### R3 MCP 连接与工具范围

用户可以配置连接器、检验可用性，并为专家选择可使用的工具。

支持三种接入方式：配置远程 MCP 服务；上传或配置 MCP 程序并在平台隔离执行环境中启动；通过本地连接组件在用户电脑启动或接入进程型 MCP 服务。三种方式均可绑定给专家。

- AC3.1：连接成功后能查看可用工具；连接失败后能看到可处理的错误原因。
- AC3.2（建议）：未授权给当前专家的工具调用被拒绝，并记录原因。
- AC3.3（建议）：凭证不以明文出现在对话、普通运行日志或可下载产物中。
- AC3.4（建议）：配置了连接器但授权失效时，任务明确显示该问题，不报告工具执行成功。
- AC3.5：每个连接器显示实际运行位置；本地连接器标明所属设备，不能让用户误以为本地路径属于平台环境。
- AC3.6：三种接入方式各完成一次工具发现和真实工具调用，结果在任务中可见；保存配置成功不等于连接测试通过。
- AC3.7：用户能够上传或配置进程型服务，并获得启动成功、启动失败或依赖缺失的明确结果。
- AC3.8：用户设备上的进程通过本地连接组件接入；用户只使用浏览器而未连接组件时，平台不能将其标记为可用。
- AC3.9（建议）：平台托管进程只能访问分配给当前用户和任务的资源，不共享其他用户的进程状态、文件或凭证。
- AC3.10（建议）：本地连接组件只接受所属用户有效会话的调用，并按用户授权的服务、目录和操作范围执行；连接设备不等于授权全部本地资源。
- AC3.11（建议）：设备离线、组件退出或进程崩溃时，将连接标为不可用，并向受影响任务显示原因；不静默切换执行位置。
- AC3.12（建议）：用户可断开设备或禁用服务；生效后拒绝新调用，已发出的调用明确显示完成、失败或结果未知，不声称已撤销外部操作。
- AC3.13（建议）：仅返回本地文件路径不能视为 Web 项目交付完成；需要回传的产物应在用户授权范围内传输，并确认 Web 端可获取后才能记为已交付。
- AC3.14（建议）：远程服务不可达、身份验证失败和进程启动失败分别给出可处理的信息，不向普通日志输出密钥。
- AC3.15：本地连接组件的首版验收在 Windows 上完成，包括连接、启动进程、调用工具、设备断线和重新连接；macOS、Linux 不在首版承诺范围。
- 待定义：首批协议兼容范围、运行语言和依赖、身份验证方式、Windows 最低版本、进程保留与清理时机。恢复规则见 R9；这里不选定隧道或进程管理技术。

### R4 提交和执行任务

用户选择单专家入口或动态专家团入口、输入需求及项目目录和文件类型要求，然后启动任务。输入附件的支持方式及大小限制仍待确认。

- AC4.1：任务启动后有唯一运行标识，用户可以查看其状态。
- AC4.2：成功时展示可访问的结果；失败时展示失败步骤和原因。
- AC4.3（建议）：任务状态区分等待、运行中、恢复中、待用户处理、成功、失败、预算耗尽和已取消，并展示原因；需要用户补充信息或处理结果未知的操作时进入待用户处理。
- AC4.4（建议）：用户可以请求取消；系统停止安排新步骤，并明确说明正在执行的外部操作是否仍可能完成。
- AC4.5（建议）：每次运行固定专家与能力配置；后续修改只影响新运行。

### R5 执行过程和产物

用户可以查看任务的可观察执行事件和最终结果，无需披露模型内部思维链。

- AC5.1：显示工具调用名称、执行状态及可安全展示的结果摘要。
- AC5.2：生成文件时，用户能在任务中找到并下载对应产物。
- AC5.3（建议）：刷新页面后仍能查看已记录的状态、事件与产物。
- AC5.4：部分步骤成功而最终任务失败时，明确标注已完成步骤和产物，不将整项任务标成成功。

### R6 多专家并行协作（首版已确认）

主专家根据用户目标拆分和分派任务，多个专家同时执行，主专家负责最终汇总。

- AC6.1：在一个至少包含两个可独立子任务的验收场景中，两个不同专家的执行时间存在重叠，证明实际支持并行执行。
- AC6.2：用户能够识别各子任务的负责专家、状态和产物，并查看最终汇总结果。
- AC6.3（建议）：每个子任务有明确的目标、输入资料、预期产物及完成条件。
- AC6.4（建议）：存在前置依赖时，后续任务等待必要输入，不以缺失或虚构的前置结果继续执行。
- AC6.5（建议）：必需子任务失败或文件缺失时，主任务不能标为成功；展示已完成结果和未完成项。
- AC6.6（建议）：任务取消后，主专家停止派发新任务，向活动子任务传播取消请求，并展示仍未结束的外部操作。
- AC6.7：动态专家团模式下，系统根据任务选定主专家和成员，仅使用用户自己的专家和用户已启用的平台预置专家，不临时创建新专家或调用其他用户的私人专家。
- AC6.8：单专家模式下，以所选专家为主专家，只能派发给用户为其预配置的协作专家；不会自动扩大到动态组团候选池。
- AC6.9（建议）：展示实际组建的专家团、各成员职责及子任务分配；候选能力不足时说明缺口，不假称已具备该能力。
- AC6.10（建议）：专家协作不传递或扩大工具权限；子专家仍按自己的能力绑定和当前用户授权执行。
- 待定义：组团是否需要用户确认、最大协作层数。预算与失败恢复见 R9。建议首版由主专家直接管理成员，成员不递归组团。

### R7 用户独立配置和使用（首版已确认）

每个用户拥有自己的专家、预置专家启用记录、Skills 配置、MCP 授权和任务；动态组团结果随任务记录。开放平台不自动意味着公开分享这些内容。

- AC7.1：用户 A 创建的私人配置、运行记录和项目文件不会出现在用户 B 的列表或搜索结果中。
- AC7.2：用户 B 即使知道用户 A 的配置、任务或产物标识，也不能通过直接访问读取、修改、启动或下载这些内容。
- AC7.3：执行用户 A 的任务只能使用 A 有权使用的凭证与数据，不能复用 B 的私人授权。
- 待定义：登录方式、首批预置内容、是否支持主动分享；在确认前不包含用户私人内容公开分享能力。

### R8 完整项目文件交付（首版已确认）

交付结果是可获取的通用项目文件集合，不能只有描述“已完成”的聊天回复。用户任务指定目录和文件类型，具体内容及质量要求依照任务约定验收，不限定为某类行业项目。

- AC8.1：任务结束时提供项目文件清单和下载入口，用户能获取与清单一致的文件。
- AC8.2（建议）：主专家汇总子专家的文件并检查必需文件是否齐全；缺失时列明缺项，不宣称完整交付。
- AC8.3（建议）：多个专家产生同路径文件时，冲突必须得到处理并记录，不允许无提示地覆盖或丢弃文件。
- AC8.4（建议）：提供项目说明，描述文件用途、使用方法、已完成验证与已知限制；仅在任务明确要求且验证通过时，声称软件项目可运行。
- AC8.5（建议）：汇总后的项目支持整体下载，保持目录结构；具体打包格式留到 Plan 决定。
- AC8.6：交付目录与文件类型符合用户明确要求；不能将纯文本改扩展名冒充其他文件格式。
- AC8.7（建议）：执行前形成任务交付清单，包括必需路径、格式、内容要求和验证方式；重要信息缺失时向用户澄清，其余假设明确展示。
- AC8.8（建议）：实际能力不支持目标格式时明确说明，不静默换格式并宣称完成。
- AC8.9（建议）：用户指定的目录均解释为当前项目内的相对路径，不允许借助路径访问其他项目或平台内部文件。
- 待定义：首批支持格式、任务交付清单是否需要确认。项目追加修改和版本要求见 R10。

### R9 预算内自动恢复（首版已确认）

子任务失败或设备离线时，系统自动尝试恢复或重新分派，在任务预算上限内推进；达到上限则停止，保留已完成结果。

- AC9.1：注入一次可恢复故障后，无需用户重新提交整个任务，系统记录恢复原因、尝试和结果，并在成功恢复后继续执行。
- AC9.2：重新分派不能突破原任务的专家候选范围或当前授权；单专家模式仍只使用预配置协作者。
- AC9.3（建议）：本地设备离线时，依赖该设备的步骤显示恢复中；独立步骤可继续。恢复不能把仅本地可访问的数据或工具假定为云端可用，也不能静默切换连接器运行位置。
- AC9.4：达到任务预算上限后停止派发新步骤及新恢复尝试，明确展示停止原因、已完成内容和剩余工作，不将任务标记为成功。
- AC9.5（建议）：主专家、子专家、重试和重分派共享同一任务预算；重新分派不重置计数。并行执行中的操作纳入预算管理，已发出的不可中断操作单独展示最终结果。
- AC9.6（建议）：恢复保留已验证的完成步骤，不无理由重做整项任务；旧尝试的迟到结果不能覆盖后续尝试已经确认的结果。
- AC9.7（建议）：外部写入发生超时或断线、执行结果未知时，优先核实结果或使用已明确保证不会重复生效的重试方式；无法核实时停止自动重复该操作并请求用户处理。
- AC9.8（建议）：已取消或预算耗尽的任务不会因设备重新上线而自动恢复。
- AC9.9：平台提供总时长与调用次数的默认值和最高限额；用户可在启动任务前调整，超出任一平台限额或填写非正数时拒绝启动并提示修正。
- AC9.10：用户未修改预算时使用平台默认值；任务展示实际生效的两个上限、已用量和停止原因，不能只显示一个含义不明的预算值。
- AC9.11：总时长或调用次数任一耗尽即停止自动推进，保存已有结果；无需同时耗尽两个维度。

#### 预算计量口径（建议，待整体验收时确认）

- 总时长从任务首次开始执行计时；初始资源排队不计入。执行后的离线等待、恢复、内部排队和待用户处理均计入，避免任务无限占用运行状态；各子专家并行时按同一任务实际经过时间计量，不将子任务时长相加。
- 调用次数为本任务实际发起的模型请求与工具执行尝试的总和，覆盖主专家、子专家、规划、汇总和重试；一次模型响应提出多个工具调用时，每个实际执行的工具分别计数。
- 已发出的调用即使失败或超时也计数；执行前因无权限、参数错误或预算不足而拒绝的调用不计为已执行；服务健康检查和用户在配置页的连接测试不计入任务调用量。
- Agent 调用一个脚本工具计为一次工具调用；脚本内部工作受独立的时间、资源及网络权限约束，不能宣称该计数覆盖脚本内部的所有外部请求。平台执行层的模型/工具自动重试也必须计数。
- 并行派发前检查剩余调用额度。剩余 1 次额度时，即使有多个专家同时申请，最多只允许 1 次新调用发出。
- 调用额度全部被已发出的请求占用时，不再派发新调用；已发出请求可在剩余总时长内完成。若其结果已满足验收条件，可成功交付；否则以预算耗尽结束，不为额外汇总或修复调用突破上限。
- 总时长耗尽后停止新增执行，并取消能够取消的在途操作；不可中断的外部操作记录最终状态，预算不是撤销外部副作用的保证。
- 每轮任务启动时固定预算；首版不在运行途中自动增加预算。平台默认值修改影响新任务，已启动任务保留其生效值。用户明确发起的新一轮修改获得独立预算。
- 数值待定：默认总时长、最长总时长、默认调用次数和最大调用次数。不将示例值当成已确认产品承诺。

#### 预算边界验收（建议）

1. 使用测试配置验证默认值生效、用户下调和上调至平台上限均有效，超过上限或非正数被拒绝。
2. 故障重试与重分派后，核对主任务总调用量包含全部已发出的尝试，计数没有重置。
3. 两个专家同时争用最后一个调用额度时，最多发出一次新调用；最后调用完成但仍缺必需文件时，任务以预算耗尽结束。
4. 本地设备持续离线且没有新调用时，总时长仍递增，达到限额后停止。
5. 新一轮修改使用独立预算，前一轮的用量与停止记录仍可查询。

### R10 项目持续修改与历史版本（首版已确认）

用户可在原项目内继续对话提出修改，系统根据已有文件和新要求生成后续版本，历史版本仍可下载。

- AC10.1：用户在已交付项目中提出修改时，系统能够引用该项目既有文件与要求，不要求重新上传全部文件或重述背景。
- AC10.2：修改完成后出现新版本，用户可以分别获取修改前后的完整文件集合。
- AC10.3：后续修改不原地覆盖历史交付版本；下载历史版本得到其原有目录和内容。
- AC10.4（建议）：每轮修改有明确的基础版本、对应运行及新增、修改、删除文件摘要；未受影响的文件保留。
- AC10.5（建议）：修改任务失败或预算耗尽时，上一成功版本仍可下载，失败尝试和部分文件不能冒充新的成功交付版本。
- AC10.6（建议）：新一轮修改使用新运行预算，自动恢复仍累计在该轮内；同时检查当前授权，不因引用历史版本而复活已撤销的凭证。
- AC10.7（建议）：同一项目首版按顺序处理修改请求；已有修改进行中时明确提示等待，避免两次修改静默互相覆盖。
- 待确认：是否允许选择任意历史版本为修改基础、历史保留时间及删除规则。可下载历史版本不等同于已支持版本回滚或分支管理。

### 首个端到端验收场景（建议测试样例，不限制产品用途）

输入：“围绕新产品发布生成文件项目。目录为 docs/brief.md、data/channel-plan.csv、copy/announcement.md。分别提供项目简报、渠道计划和宣传文案，三份文件中的产品名称、发布日期和预算口径必须一致。”样例使用合成业务资料，不依赖联网获取事实。

验收：三个文件路径与格式正确、内容满足各自要求、共用事实一致，并可整体获取；至少两个独立文件由不同专家并行生成。该样例不能代替后续二进制格式、脚本执行和 MCP 调用的独立验收。

1. 用户 A 配置所需专家、Skills、MCP 授权及协作关系。
2. A 选择专家或专家团并输入一个有明确交付要求的项目任务。
3. 主专家拆分任务，至少两个独立子任务由不同专家并行执行。
4. 主专家汇总和检查项目文件，展示各子任务状态及交付清单。
5. A 下载完整项目并按该项目类型的标准验收；用户 B 无法访问该项目。
6. 注入一个必需子任务失败的情况，验证平台明确显示未完成项，不将部分文件冒充完整项目。

### MCP 三种运行位置的验收场景（建议）

对同一类可控测试工具分别使用远程、平台托管、本地设备三种接入方式：读取一份测试资料并产生一个文件，验证工具发现、调用结果、项目文件获取和运行位置展示。

另行覆盖：本地设备离线；连接撤销后继续调用；平台进程启动失败；其他用户尝试使用该连接；本地文件已生成但回传失败。每种异常都应有明确状态，不把不完整结果标记为成功。外部写入的超时或断线不能自动解释为未执行，恢复与重试遵循 R9。

### 自动恢复与版本迭代验收（建议）

1. 在 Windows 本地工具调用前制造断线，验证任务自动进入恢复流程；预算内重新连接后继续执行。
2. 持续制造故障，验证原任务预算累计生效、达到上限后停止；之后重新连接不自动重启已停止任务。
3. 完成交付 V1，在同一项目对话中请求调整渠道预算，生成 V2；验证相关文件一致更新、未涉及文件保留，V1 和 V2 均可独立下载。
4. 制造下一轮修改失败，验证 V2 仍为可用成功交付，部分文件单独标明，不覆盖 V1 或 V2。

## 5. 建议的首版范围边界

以下边界待用户确认：

- Web 是主要配置和任务入口；本地连接组件属于首版范围，用于已授权的进程型 MCP 服务及所需文件传输。通用桌面点击、屏幕控制不因支持本地 MCP 而自动纳入范围。
- 暂不包含公开技能市场、付费交易、IM 接入和定时自动化。
- 暂不承诺任意第三方 Skill 或 MCP 服务均能兼容，先确定验收所需的兼容范围。
- 不在本 Spec 中预设前后端框架、数据库、队列、编排框架或数据表设计。

## 6. 质量与执行约束（待量化）

- 不同用户的私人配置、任务、凭证和产物相互隔离；同一用户的独立任务也不能意外串用上下文或文件。
- 失败、超时和取消必须可辨认，不能仅无限显示加载状态。
- 外部写入操作重试时，需要定义避免重复提交的行为；超时不等于外部操作一定未发生。
- 单任务总时长和调用次数采用平台默认值、平台最高限额与用户范围内调整机制；具体数值及并发上限待定。费用如可统计应与执行预算区分，不承诺调用次数可换算为固定费用。
- 性能阈值、任务记录保留时间、文件大小与支持格式尚未确定，不填写无依据的指标。
