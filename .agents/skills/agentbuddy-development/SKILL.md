# AgentBuddy 项目开发

按“分析 → Spec → Plan → 实现 → Test → Check → 维护”推进，建立需求与验证证据的对应关系。按任务规模裁剪，不为简单修正制造整套文档。

## 入口与范围

1. 定位仓库根目录，检查 `docs/specs/platform.md` 和项目标识。默认位置为 `<repo>/.agents/skills/agentbuddy-development/`；不得依赖个人电脑的绝对路径。复制到其他位置后仍须定位实际仓库，找不到时询问位置，不套用到无关项目。
2. 阅读适用的 `AGENTS.md`、当前请求、`git status`、当前 Spec 相关章节，再查有关代码及已有计划。归档和调研不是现行要求。
3. 最新用户明确决定优先；Spec 是产品基线，代码提供现状证据。实现缺陷按 Spec 修复；产品变化先同步相关 Spec，不削弱验收以迁就错误代码。
4. 判断当前任务是分析/Spec、Plan、实施、测试评审还是维护。只做 Spec/Plan 不改应用代码；已授权实施时完成必要步骤，不在阶段间反复索要确认。
5. 只对会改变范围或外部行为的关键缺口提问。普通技术选择依据已有约定决定并记录；缺少外部服务时继续独立可完成的本地工作。

## 项目约束

以当前 Spec 为准；以下为首版基线，用户变更时同步本 Skill，避免重复信息漂移：

- React + TypeScript + Vite；Python + FastAPI；AgentScope 2.0 系列 Python 编排；独立 Python 执行进程；SQLite 和本机文件目录。
- 页面基路径默认 `/app`，业务 API 默认 `/api/v1`；事件、下载、健康检查和接口文档使用统一后端前缀配置，由根路由统一挂载。前后端分离可同域部署。
- 可信用户、单机工作空间，无沙箱或复杂安全体系。不自行引入多租户、跨设备组件、Redis、PostgreSQL、对象存储或分布式部署。
- 远程 MCP 与后端机器进程型 MCP；浏览器电脑不等同于后端机器。
- 固定总控、已有专家、单层有限并发；Skill 指令必须配合真实工具执行。
- 工作目录、超时、取消、有限重试、共享预算、不可覆盖的成功版本属于功能正确性要求，不能以“无安全要求”为由移除。

## 1. 分析与 Spec

- 将请求对应到当前 Spec 的功能与验收编号，当前基线为 F1–F10、场景 A–F；编号变化时以文件为准。
- 明确触发条件、可观察的预期行为、失败行为和范围外内容。区分已确认要求、实现假设和待决产品问题。
- 查明实际接口、模型、执行流程、文件及测试。没有代码时明确尚未实现，不虚构已有模块。
- Bug 先取得可重现输入、日志或失败测试；需求变化更新 Spec，等价内部重构不制造新产品需求。
- 完成标准：本次改什么、什么算通过、哪些依赖缺失均清楚。仅分析的请求到此交付。

## 2. 制定计划

跨模块工作按 [记录模板](references/work-records.md) 写入或更新 `docs/plans/<task-slug>.md`；小修复用简短步骤即可。

- 覆盖受影响模块、API 契约、数据/文件变化、执行状态、前端行为和验证方式。
- 按可验证的纵向切片排序，例如“绑定 Skill 并真实生成文件”；避免先做所有空壳页面，最后才验证执行内核。
- 每项任务包含依赖、验收编号、预期结果和验证方式；可标注独立工作，但本 Skill 不要求调用子代理。
- 对迁移、进程管理、版本文件等实际风险说明失败恢复办法；备份同时考虑 SQLite 和项目文件。
- 从工程配置发现路径与测试命令。尚无工程结构时记录初始化选择，不把推测写成已存在事实。
- 完成标准：步骤可落地、验收有验证方式、关键行为不留给实现时猜测。只要求 Plan 时到此交付。

## 3. 实现

- 按授权范围逐个切片实施和验证，保留用户已有改动，不顺带改写无关模块。
- 模型与外部工具等待不能跨 SQLite 写事务；阻塞脚本和长任务不能占住 HTTP 请求处理流程。
- 前后端契约一致；加载、空结果、失败、等待和取消有可观察表现。连接配置保存不代表连接实际可用。
- 变更契约时同步调用方、配置及相关文档。SDK/API 不明确时查官方资料，不编造接口。
- 模拟可用于测试，不得包装为真实集成完成；实服务测试只使用已授权环境，缺少配置则记录限制。
- 完成标准：本次用户行为贯通，而不仅是代码存在或构建通过。

## 4. Test

按改动选择 [验证指南](references/verification.md) 中的检查，不无差别执行昂贵全量测试。

- 状态机、预算并发、恢复、迁移和历史版本优先用测试固定行为再实现；普通文案或低影响可逆变动不强制 TDD。
- 先最小相关测试，再做受影响模块类型检查、构建或集成验证。无新改动或疑点时，不重复已通过检查。
- 脚本、进程型 MCP 和文件产物需要真实集成证据。可控 MCP 服务证明协议集成，不代表外部供应商联通已验证。
- UI 变更验证实际交互和错误状态，不能只凭后端测试宣布端到端通过。
- 记录命令、结果、环境和未覆盖项。未执行写未执行，服务不可用写受阻，不能写通过。

## 5. Check 与交付

Test 验证具体行为；Check 对照请求和 Spec 判断是否整体完成。

- 逐项核对本次验收、实际实现和证据，发现测试未覆盖的遗漏。
- 查看 diff 的范围外改动、废弃配置、错误终态、失效引用和遗漏的页面路径。
- 要求下载时检查文件内容及格式；要求版本保留时检查历史内容未变；口头声明不能代替交付结果。
- 更新计划及验证记录，仅有证据满足的项标记完成。
- 回复说明变更、验证和剩余问题；代码实现完成但真实集成受阻时分开报告。

## 6. 维护

- Bug：复现 → 根因 → 最小修复 → 必要回归 → 更新记录；不增加重试掩盖确定性错误。
- 需求变化：同步 Spec → 调整受影响计划/契约 → 实现与验证，不重开全部已确认需求。
- 重构：明确保持不变的行为，通过相关测试与调用方验证等价，不扩展产品范围。
- 依赖/数据库升级：检查实际版本和官方兼容说明，验证迁移及旧数据可读性；不覆盖用户真实项目做测试。
- 更新实际受影响的启动说明、配置示例和维护记录，不创建空文档。不要自动修改个人记忆。
- 下次接续读取当前 Spec、计划状态及最新验证记录；不把旧版本的验证结果当作新代码已通过。

## 调用示例
